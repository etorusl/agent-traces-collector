# Контракт данных

`schema_version=1`. В одном каталоге запуска — одна фиксированная конфигурация.

```text
runs/<experiment>/
  manifest.json                  конфигурация, runtime, SHA исходников/данных, git
  server.json                    ответ GET /v1/models
  .lock                          блокировка единственного writer
  attempts/<attempt-id>/
    started.json                 сведения для восстановления
    events.jsonl                 последовательная трасса
    summary.json                 атомарный итог попытки
    workspace/                   отдельная рабочая папка GAIA
```

Дополнительно AppWorld пишет штатные логи/состояние в
`<appworld_root>/experiments/outputs/collector-<attempt-id>/`.
Все эти данные игнорируются Git по умолчанию.

## Вход предиктора

Единственный признак:

```json
{"features":{"user_request":"What is 2 + 2?"}}
```

Строка берётся из AppWorld `instruction` или GAIA `Question` без добавления
контекста. Экспортёр использует явный allowlist; не сохраняет в `features`
историю, reasoning, вложения, имена файлов, инструменты, уровень, эталонный
ответ, annotator metadata, supervisor, системный промпт или состояние мира.

`targets` и `provenance` — отдельные объекты. Не используйте их как входные
признаки. Фиксированную конфигурацию выбирают на уровне эксперимента, а не
предсказывают из полей строки.

## Счётчики

| Поле | Значение |
| --- | --- |
| `generated_tokens` | Сумма серверных completion tokens, включая reasoning, код, действия и финальный ответ |
| `reasoning_tokens` | Серверный breakdown reasoning; `null`, если неизвестен хотя бы для одного вызова |
| `non_reasoning_tokens` | Разность двух предыдущих; может включать форматирование/служебные токены по определению сервера |
| `response_tokens` | В режиме output IDs — реальные токены вне reasoning и его маркеров, включая EOS; иначе `null` |
| `reasoning_overhead_tokens` | В режиме output IDs — число сгенерированных токенов маркеров reasoning; токены из prompt не включаются |
| `prompt_tokens` | Сумма input tokens каждого вызова, с повторным учётом передаваемой истории |
| `observed_*` | Только известная часть счётчика; не заменяет полный target |
| `*_coverage` | Число известных вызовов и всех попыток HTTP-запросов |
| `cached_prompt_tokens` | Серверный per-call cache breakdown, если доступен; сохраняется в событиях |
| `text_token_estimates` | Опциональный пересчёт видимых текстов тем же tokenizer; отдельный источник |

Наличие отдельного текста reasoning не означает наличия точного server-side
счётчика. Старый vLLM может прислать `reasoning_content` и только общий usage.
Сохраняется общий generated target, reasoning остаётся неизвестным. При
tokenizer-оценке не делается предположение, что текстовая ретокенизация
воспроизводит реальные output token IDs, EOS или маркеры thinking.

В явно включённом режиме `token_id_format` счётчик reasoning получается из
реальных output IDs: учитываются только токены внутри верифицированных маркеров,
без заголовков канала и закрывающего маркера. Отдельно сохраняются
`reasoning_overhead_tokens` и `response_tokens`. Их сумма с `reasoning_tokens`
совпадает с `generated_tokens`. Маркеры в prompt не считаются генерацией.
Если число output IDs не совпало с `completion_tokens` или отсутствуют prompt IDs,
точный reasoning не выдаётся. Это не tokenizer-оценка; источник — `output_token_ids`.

`usage_complete` относится к generated tokens. `reasoning_complete` относится
к reasoning. Пустой набор LLM-вызовов имеет нулевую генерацию; ошибки setup
при этом всё равно не являются решёнными задачами.

## Время

| Поле | Интервал |
| --- | --- |
| `setup_seconds` | Создание процесса, загрузка мира/копирование вложений, подготовка окружения |
| `agent_seconds` | От готового окружения до остановки агента: LLM, сеть/очередь, инструменты, ретраи/backoff, протокол и запись событий |
| `metrics.llm_seconds` | Сумма длительностей отдельных HTTP-попыток; не включает паузы между ретраями |
| `tool_seconds` | Время запросов к инструментальному процессу, включая IPC |
| `evaluation_seconds` | Официальная проверка результата после остановки агента |
| `end_to_end_seconds` | Setup, работа, оценка и закрытие окружения; без предварительной загрузки датасета/токенизатора и финальной записи summary |

Используется `time.perf_counter()` в родительском процессе, в котором AppWorld
не замораживает время. Длительность не выводится из числа токенов.
Non-streaming режим не даёт TTFT и времена отдельных output tokens; такие
поля намеренно не выдумываются. Для vLLM это длительность с точки зрения
клиента, не чистое GPU execution time.

После жёсткого прерывания незавершённой попытки длительности восстановить
точно нельзя: `agent_seconds=null`. Сохранившиеся счётчики остаются доступными.
Незавершённый `llm_started` учитывается как неизвестная генерация. Если
`attempt_finished` уже записан, а summary ещё нет, summary восстанавливается
из терминального события.

## Завершение и оценка

`status=finished` означает, что агент остановился: выдал `final_answer` либо
AppWorld сообщил `task_completed()`. Это **не** свидетельство правильности.

- AppWorld: `success` берётся из штатного `TestTracker.success` после `world.evaluate()`.
  Успех требует правильного конечного состояния без недопустимых изменений.
- GAIA validation: числа, упорядоченные списки и строки сравниваются по
  алгоритму официального leaderboard scorer. Эталонный ответ не попадает в промпт.
- GAIA test и ошибки оценщика: `success=null`, а не `false` и не `true`.

Остальные статусы: `max_steps`, `token_budget`, `deadline`, `model_length`,
`missing_usage`, `protocol_error`, `tool_timeout`, `llm_error`, `setup_error`,
`setup_timeout`, `collector_error`, `interrupted`.

`censored=true` означает незавершённую работу из-за остановки/ошибки. При
`finished` с неверным ответом `censored=false`, `success=false`: стоимость
завершённой попытки известна, стоимость успешного решения не наблюдалась.
Частично решённая задача при исчерпании бюджета также не становится успешной
меткой в стандартном экспорте, даже если state-based evaluator что-то зачёл.

## Экспорт и будущая выборка

Стандартный экспорт требует `success=true`, `censored=false`, `usage_complete=true`.
`--include-unsolved` сохраняет диагностические строки, не превращая `null` в нули
и не удаляя признак цензурирования. `target_semantics` указывает, идёт ли речь о
проверенно успешной работе или расходе до остановки.

Экспорт не делает train/test split и не обучает модель. Для будущего разбиения:

- сохраняйте все попытки/повторы одной задачи вместе;
- используйте `task_group` для AppWorld-сценариев с общим префиксом ID;
- держите одинаковые запросы с одним `request_sha256` в одной части;
- не смешивайте конфигурации агентов/моделей без отдельного экспериментального дизайна;
- оценивайте долю неуспехов: фильтрация только успехов меняет распределение задач.

Поскольку содержимое вложений и окружение скрыты от предиктора, даже одинаковый
текст может иметь разную стоимость решения. Такие данные не следует дополнять
скрытыми признаками для искусственного улучшения точности будущей модели.
